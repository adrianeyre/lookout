# P1: the socket proxy and the Host's loopback — findings

**Scope issue:** #66 · **Date:** 25 November 2026 · **Status:** done; findings fixed and verified 25 November 2026, except #102, accepted. In-process probes, and deployment probes in both configurations, run before and after the fixes.

Hypothesis: [H2](../../product-requirements-document/pen-testing.md#h2-the-socket-proxy-hands-docker-to-every-process-on-the-hosts-loopback--critical). Probe tests: [`apps/server/src/pen-test/probes/p1-proxy.test.ts`](../../../apps/server/src/pen-test/probes/p1-proxy.test.ts), which runs in `pnpm test`, and [`p1-proxy.probe.ts`](../../../apps/server/src/pen-test/probes/p1-proxy.probe.ts) against the deployment (`pnpm pen-test:probe`); each deployment `today_…` probe's `it.fails` partner is the in-process one. Private on the same terms as the PRD.

"In-process" here means the shipped `compose.socket-proxy.yaml` read as data: its listener flags, and its allowlist anchored and matched against the percent-decoded path with the query left out, as the file's own comment says wollomatic matches. That is a model; every request it reasons about is also sent to the real proxy in the deployment. In the deployment "the Host" is the throwaway daemon's container: the proxy runs in its network namespace exactly as shipped, a **Host user** is `docker exec --user 65534:65534` into it (nobody, in no docker group), and a **host-network Container** is the fixture Image run with `--network host --user 65534:65534`.

The PRD's table makes it **critical** when "anyone without the password reads … an environment value, carries out a Container Action, or reaches Docker". A local user outside the docker group, or a host-network Container, has no password and gets exactly that, with only a foothold on the Host. It is confined to the opt-in configuration, which is the one recommended as hardening, so it does not lower the severity: the hardening makes the Host weaker for everyone who is not already root-equivalent. Lookout's session secret is no longer enough to mint a cookie (#80's fix mixes in the password hash and a random value chosen at start), so the read does not become a Lookout session; but the password hash can be attacked offline, and every other Container's secrets are read directly.

## Findings filed

### #101 (F-P1-1): With the socket proxy, any process on the Host's loopback reads every Container's environment and restarts and removes Containers, without the password or the docker group

- **Severity: critical.** Anyone without the password reads environment values and carries out Container Actions (PRD severity table), from a foothold on the Host or a host-network Container.
- **Rule broken:** ADR-0011, "Those can do no more than the allowlist permits, which is less than the docker group already allows any local user it includes" (untrue for users outside the group, and no recorded end). PRD, "A secret is shown only when asked for, one at a time", and FR-20's logged reveal, both bypassed. ADR-0003's premise that Docker access is the docker group's.
- **Configuration:** `compose.socket-proxy.yaml` only. The default configuration is sound here.
- **Steps:** on the Host, as any user (or in any Container with `network_mode: host`), `wget -qO- http://127.0.0.1:2375/containers/lookout/json`; `curl -X POST http://127.0.0.1:2375/containers/<id>/stop`; `curl -X DELETE 'http://127.0.0.1:2375/containers/<id>?force=true&v=true'`.
- **Observed:** `200` with every Container's environment, Lookout's `LOOKOUT_PASSWORD_HASH` and `LOOKOUT_SESSION_SECRET` among them; `204` for the actions; the Container and its volume are gone. **Expected:** only Lookout can reach the proxy (a Unix socket in a volume only the two Containers mount, or a credential), so nobody on the Host gains Docker access by Lookout being installed.
- **Impact:** installing the hardening turns any local foothold (a compromised web app, a service account) into every Container's secrets and the power to stop or destroy any Container and its data.
- **Test that would have caught it:** `P1 H2: who can reach the proxy › only Lookout can reach the proxy: a socket only its Container mounts, not a loopback port` (`it.fails` today), with the deployment's `today_` probes above.

### #102 (F-P1-2): The proxy allows a forced remove with volumes, which Lookout never sends and ADR-0005 forbids

- **Severity: medium.** A boundary has no defence in depth: the allowlist is documented as "exactly the endpoints in ADR-0005", but ADR-0005's remove never force-removes a running Container and never deletes volumes, and the proxy cannot see the query that asks for both.
- **Rule broken:** ADR-0005, "Remove never deletes volumes and never force-removes a running Container"; ADR-0011 and the comment in `compose.socket-proxy.yaml` ("Exactly the endpoints in ADR-0005"; "remove them, and nothing else").
- **Configuration:** `compose.socket-proxy.yaml`.
- **Steps:** through the proxy, `DELETE /containers/<running id>?force=true&v=true`.
- **Observed:** `204`; the running Container and its anonymous volumes are deleted. **Expected:** refused, or the gap recorded in ADR-0011 as accepted with the date it stops being true.
- **Impact:** with #101 (F-P1-1) any loopback process, and after #101 (F-P1-1)'s fix a compromised Lookout, can destroy data that Lookout's own remove never could. Small once #101 (F-P1-1) is fixed.
- **Test that would have caught it:** `P1 H2: the allowlist bounds the path, not the query › a forced remove of a running Container with its volumes is refused` (`it.fails` today).

## Load and reach

No request left the pen-test deployment: the deployment probes run only inside its throwaway daemon (the daemon's own container, and one-off fixture Containers in its namespace) or against `127.0.0.1:7780`. Only a Container made for the purpose (`p1-sacrificial`) is restarted and removed; the fixtures are only read. Requests are sent one at a time; nothing runs in parallel. The in-process probes open no socket.
