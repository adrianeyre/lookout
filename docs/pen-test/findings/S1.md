# S1: Hosted Site checks and label trust — findings

**Scope issue:** #67 · **Date:** 25 November 2026 · **Status:** done; findings fixed and verified 25 November 2026. In-process probes, and deployment probes in both configurations, run before and after the fixes.

Hypothesis: [H4](../../product-requirements-document/pen-testing.md#h4-image-publishers-not-the-operator-choose-what-lookout-fetches--medium). Probe tests: [`apps/server/src/pen-test/probes/s1-sites.test.ts`](../../../apps/server/src/pen-test/probes/s1-sites.test.ts) and [`s1-dial.test.ts`](../../../apps/server/src/pen-test/probes/s1-dial.test.ts), which run in `pnpm test`, and [`s1-sites.probe.ts`](../../../apps/server/src/pen-test/probes/s1-sites.probe.ts) against the deployment in both configurations (`pnpm pen-test:probe`); each deployment `today_…` probe's `it.fails` partner is the in-process one. Governing documents: ADR-0010 and every item of the [v1.1 review](../../security-review-v1.1.md).

"In-process" means the real app runs against the fake Docker, with the real check engine connecting only to listeners the test starts on `127.0.0.1`. Docker merges an Image's `LABEL`s into its Container's labels and Lookout reads only the merged set, so in-process a Container label stands for one an Image publisher wrote; the deployment probe builds a real Image with `LABEL`s to show the merge. Link-local, metadata and private addresses are never dialled: they go to a recording checker (`s1-sites.test.ts`) or to the real check engine with `node:http`'s `request` stubbed (`s1-dial.test.ts`), which shows the address it would connect to. These probes don't depend on the configuration, except where a row says otherwise.

### #103 (F-S1-1): Image publishers, not the operator, choose which Host and network addresses Lookout's checks reach

- **Severity: medium.** A boundary has no defence in depth, and a documented acceptance (ADR-0010, v1.1 review item 3) rests on a premise that is untrue for Image `LABEL`s and records no end. Not critical: the Container gets nothing back (only the signed-in owner sees the result), the request is one GET with no body, and the socket proxy's port answers GETs with reads only.
- **Rule broken:** PRD, "A Container is an input … nothing from them is trusted, rendered as markup, fetched unbounded". ADR-0010's "anyone who can label a Container already controls Docker, so trusting labels adds no new access" and v1.1 review item 3's acceptance, which name no date or condition on which they stop holding.
- **Steps:** build an Image with `LABEL lookout.url="http://admin.internal:9101/admin/flush?all=1,http://169.254.169.254/latest/meta-data/iam/security-credentials/"` and `LABEL lookout.check=public` (or a Traefik rule `Host(\`169.254.169.254\`)`); run it with no labels of the operator's; open the Websites page.
- **Observed:** at the Host, Lookout sends `GET /admin/flush?all=1` with `Host: admin.internal:9101` to whatever listens on the Host's loopback port 9101, and the page shows its status, timing and `Location`. In public mode it connects to `169.254.169.254:80`, to private and ULA addresses, and to whatever a name resolves to, with no address filter. **Expected:** label-named check targets are bounded by what the operator chose: at the Host, only ports the Container publishes (or the Traefik entrypoints); in public mode, no loopback, link-local, metadata or private address, checked on the resolved address at connect time.
- **Impact:** any Image the operator pulls can make Lookout probe the Host's loopback and the LAN (and in a cloud, the metadata service) from the Host's network, with GETs and paths of its choosing. Blind to the Container, but a state-changing GET on a local admin service, or a scan read back from the owner's screen, are in reach.
- **Test that would have caught it:** `S1 H4 › checks no Hosted Site an Image names at a loopback, link-local or private address in public mode`; `› a label cannot point checks at another service's loopback port and path`; `› a name that resolves to loopback is not dialled in public mode (DNS rebinding)`; `s1-dial.test.ts › in public mode, never dials a link-local, metadata, loopback or private address`.

### #104 (F-S1-2): One Container's labels crowd the operator's own `LOOKOUT_SITES` out of the 500 Hosted Sites

- **Severity: medium.** A control (the operator's own Hosted Site checks) is weaker than the v1.1 review says: its finding "checks at most 500, the first by URL" bounds work but lets any Container decide which 500.
- **Rule broken:** PRD, "A Container is an input"; v1.1 review "Findings fixed" (the 500 cap); PRD §14's Hosted Sites from `LOOKOUT_SITES`.
- **Steps:** run a Container (or an Image) labelled `lookout.url=http://a000.example/,…,http://a499.example/` beside `LOOKOUT_SITES=https://shop.example/`.
- **Observed:** the Websites page lists the 500 labelled sites; `https://shop.example/` is gone, unchecked, and Check now on it is 404. Only a server-log warning says so. **Expected:** `LOOKOUT_SITES` is always checked; labelled Hosted Sites share what is left of the cap (and, better, each Container has its own small cap), and the page says when some were dropped.
- **Impact:** a Hostile Container silently switches off the owner's monitoring of their own sites, so an outage it causes goes unseen.
- **Test that would have caught it:** `S1 H4: 500 labelled Hosted Sites crowd out LOOKOUT_SITES › the operator's LOOKOUT_SITES are always checked, whatever Containers label`.

### #105 (F-S1-3): An Image's `lookout.self=true` makes its Container unstoppable from Lookout

- **Severity: low.** A documented decision (FR-26: the label marks Lookout's own Container) with no recorded end, assuming the operator writes it. Nothing is gained beyond Lookout's refusal: Docker still stops it.
- **Rule broken:** PRD, "A Container is an input"; FR-26 and ADR-0005 intend `lookout.self` for Lookout's own Container and its proxy only.
- **Steps:** run an Image built with `LABEL lookout.self=true`; try stop, restart or remove from Lookout, or reveal an environment value.
- **Observed:** 403 `Lookout cannot act on its own Container` for every action and for the reveal. **Expected:** only Lookout's own Container (and its proxy) is self: for example, the label must match a value Lookout's own configuration holds, or the Container ID Lookout reads for itself, never a label an Image can carry.
- **Impact:** a Hostile Container (a miner, say) cannot be stopped from the dashboard, which is where the owner would see it; its environment is hidden from the reveal.
- **Test that would have caught it:** `S1 H4: lookout.self from an Image › a Container that is not Lookout cannot make itself unstoppable by its labels`.

## Load and reach

No request left the process or the deployment: in-process checks connected only to listeners on `127.0.0.1` started by the test, link-local, metadata and private addresses went only to a recording checker or to a stubbed `node:http`, and the one name resolved (`localhost`) resolves from the hosts file. The deployment probe checks its labelled URLs at the Host only, against a recorder on the daemon's loopback and the socket proxy's port; it never sets `lookout.check=public`. The largest demonstration was one request at a time.
