Hypotheses: [H4](../../product-requirements-document/pen-testing.md#h4-image-publishers-not-the-operator-choose-what-lookout-fetches--medium) (the documents' half), [H5](../../product-requirements-document/pen-testing.md#h5-a-session-never-really-ends--medium) and [H7](../../product-requirements-document/pen-testing.md#h7-behind-an-https-reverse-proxy-the-cookie-becomes-secure-looks-untrue--medium) (as the documents stand after #99). "In-process" means the real app against the fake Docker (configuration-independent). The documents read: [v1 review](../../security-review-v1.md), [v1.1 review](../../security-review-v1.1.md), the README's Security section, and every ADR. Items another scope issue owns are marked so and not re-probed here.

## Findings to file

### #107 (F-V1-1): The v1 review and ADR-0003 say Host filesystems are only `statfs`ed; the Largest folders walk lists every folder

- **Severity: medium.** A control is weaker than its security review says.
- **Rule broken:** v1 review item 4 ("mount points … are only `statfs`ed, never read"); ADR-0003 ("All Host Metrics are read from `/host/proc`, `/host/sys`, and `statfs`"). The PRD's high row names "a Host file read beyond `statfs`" for a session; this is a directory listing, documented in FR-14a, not a file read, but the security documents were never updated.
- **Steps:** `walkFilesystem` on a Host root with `/home/alice/private-notes`; or sign in and read `GET /api/folders` after a scan.
- **Observed:** every readable directory of every real filesystem is opened and its path can reach the browser. **Expected:** the review and ADR-0003 say so, and what bounds it (no symlinks followed, one filesystem, UID 1000's view, names only).
- **Test that would have caught it:** `V1 v1 review item 4 and ADR-0003 › the v1 review and ADR-0003 say Lookout lists the Host's folders, not only statfs`.

### #103 (F-V1-2): ADR-0010, the v1.1 review and the README trust labels as the operator's, but any Image's `LABEL`s are labels

- **Severity: medium.** The acceptance rests on "whoever controls a Container's labels already controls Docker", which an Image publisher breaks without any Docker access.
- **Rule broken:** ADR-0010 ("Anyone who can label a Container already controls Docker"), v1.1 item 3 and its second accepted risk, README "Hosted Site checks only reach what you configured".
- **Observed:** labels from an Image choose Hosted Sites (metadata and loopback ports included) and `lookout.check=public`. **Expected:** the documents name Image labels as a source and record the decision (or the code tells the two apart). The behaviour itself is S1's (H4); file once with S1's finding if S1 files one, citing both.
- **Test:** `V1 H4 › ADR-0010, the v1.1 review and the README do not rest on "whoever labels a Container controls Docker"`.

### #131 (F-V1-3): Accepted risks record no date or condition when they stop being true

- **Severity: low** (a documented decision with no recorded end).
- **Where:** ADR-0003, ADR-0008, ADR-0010, ADR-0011; the "Accepted risks" of both reviews.
- **Test:** `V1 ADRs and reviews that accept a risk record when it stops being true › …` (six `it.fails`).

### #132 (F-V1-4): Two security claims overstate the code

- **Severity: low** (documentation drift; the code is sound).
- **Where:** the v1 review's accepted risk "Behind an HTTPS reverse proxy the cookie becomes `Secure` automatically" (only with `X-Forwarded-Proto: https` or `LOOKOUT_SECURE_COOKIE=true`, and the name in `LOOKOUT_HOSTNAMES`); the README's "answers only on its own addresses" (any IP address is answered).
- **Tests:** `› the v1 review says what makes the cookie Secure …`; `› the README says which Host headers Lookout answers …`.
