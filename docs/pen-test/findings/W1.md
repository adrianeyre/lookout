## Findings filed

### #87 (F-W1-1): Lookout answers on any `Host`, so a rebound name signs in from any page the owner visits

- **Severity:** medium. A boundary has no defence in depth: the password still stands, so it is not critical, but the `Origin` check, the only CSRF defence besides `SameSite`, is defeated whenever the attacker controls the name the browser uses.
- **Rule broken:** PRD H6; ADR-0008 (reachable only over the LAN or VPN); FR-34 (state-changing requests come from this origin). Check "Internal headers are trusted only when the server set them".
- **Steps:** `POST /api/login` with `Host: evil.example`, `Origin: http://evil.example` and the password; then `GET /api/containers` and `POST /api/logout` with the same headers and the cookie.
- **Observed:** 204 with a session cookie, 200 with the Container list, 204.
- **Expected:** a request whose `Host` is not one Lookout is configured to answer to (its bind address, or names the operator lists) is refused before any route.
- **Impact:** a page the owner visits rebinds its own name to `127.0.0.1` or the LAN address and runs password guesses from the owner's browser (counted against the owner's address, so it can also lock the owner out, H3); with a right guess, or a password the browser autofills, the attacker's origin holds a session with the whole API, Container Actions and environment reveal included.
- **Test that would have caught it:** `w1-browser.test.ts` › `refuses to sign in on a Host that is not Lookout's own` (today `it.fails`).

### #88 (F-W1-2): The Server-Sent Event streams carry no security headers and are cacheable

- **Severity:** medium. A control is weaker than its security review says: the v1 review, item 6, says the headers and `Cache-Control: no-store` are on every page, asset, API answer and error. The practical impact is small: `text/event-stream` is not rendered, and the streams need a session.
- **Rule broken:** v1 security review item 6; PRD "Checks every scope issue carries" (security headers on every response, W1's "every response's security headers and CSP").
- **Steps:** sign in; open `/api/stream`, `/api/containers/stats` or `/api/containers/<id>/logs?tail=100`; read the response headers.
- **Observed:** only `content-type`, `cache-control: no-cache, no-transform`, `connection`, `x-accel-buffering`. `reply.hijack()` (`app.ts:329`) bypasses the `onSend` hook that sets the rest.
- **Expected:** the same `Content-Security-Policy`, `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`, COOP, CORP and `Permissions-Policy` as every other answer, and `no-store`.
- **Impact:** Container names, labels, Host Metrics and log lines may be kept by a cache that honours `no-cache` but not `no-store` semantics, and the streams lack the defence-in-depth headers the review promises.
- **Test that would have caught it:** `w1-browser.test.ts` › `sends them, and no-store, on every Server-Sent Events stream` (today `it.fails`).

### #89 (F-W1-3): Bidirectional controls from a Container are shown unisolated

- **Severity:** low. Hygiene: no markup or script, but the owner can be shown text that is not what the Container holds.
- **Rule broken:** PRD check "A Container is an input"; W1 probe "control, ANSI and bidirectional characters".
- **Steps:** run a Container with a label, environment variable name, mount or log line containing U+202E (for example `invoice<U+202E>txt.exe`); open its detail.
- **Observed:** the text is inserted as is, with no `<bdi>`, `dir="auto"` or `unicode-bidi: isolate`, so it reorders what follows it in the same line.
- **Expected:** text from a Container is isolated (or its bidirectional controls shown visibly), so it cannot reorder its neighbours.
- **Impact:** a Hostile Container can disguise a label, a mount source or a log line, for example making a host path or a URL read as something else.
- **Test that would have caught it:** `pen-test-w1.test.tsx` › `isolates bidirectional text from a Container, so U+202E cannot reorder it` (today `it.fails`).

### #90 (F-W1-4): `no-store` is chosen by URL prefix, so a percent-encoded API path is cacheable

- **Severity:** low. The same control as #88 (F-W1-2), missed by a different route: it needs a session and a URL the owner would not type, and `SameSite=Strict` stops a cross-site link from carrying the cookie. It may be fixed with #88 (F-W1-2).
- **Rule broken:** PRD check "Middleware that matches by path matches by segment"; v1 security review item 6.
- **Steps:** signed in, `GET /%61pi/containers`.
- **Observed:** 200 with the Container list and no `Cache-Control` (`app.ts:260` tests `request.url.startsWith('/api/')` on the raw URL; the router decodes `%61`).
- **Expected:** `no-store` decided by the matched route (`request.routeOptions.url`), not by the raw URL text.
- **Impact:** an API answer may be stored by the browser's cache under that URL.
- **Test that would have caught it:** `w1-browser.test.ts` › `marks every API answer no-store, however its path is spelled` (today `it.fails`).

## Load and reach

No request left the pen-test deployment: the deployment probes ran only against `127.0.0.1:7780` or inside its throwaway daemon, and its isolation probe (`e1-isolation.probe.ts`) passed in the same run, in each configuration. The in-process probes opened no socket beyond the app's own. The largest demonstration was one browser and one request at a time.
