## Findings filed

**#80 (F-A1-1) · A stolen or minted session outlives a password change** · `severity:medium`

- **Severity:** medium (triaged down from the draft's high): the control ADR-0008 documents, changing the password, ends no session. The high part of the chain, a session reading the secret, is K1's #79 (F-K1-1), filed as high; with it this becomes durable access.
- **Rule broken:** ADR-0008 (changing the password is the remedy for a leaked password); PRD success criterion 5 (H1).
- **Steps:** sign in (or mint a cookie: base64url JSON `{"sid":…,"seen":<now>}` + `.` + base64url HMAC-SHA256 with the secret); set a new `LOOKOUT_PASSWORD_HASH` and recreate the Container; send the old cookie to `/api/session`.
- **Observed:** 200. **Expected:** 401; changing the password ends every session.
- **Impact:** a leaked cookie or secret keeps root-equivalent access until someone thinks to rotate the secret, which nothing documents.
- **Test that would have caught it:** `a session minted before a password change is refused after it`.

**#81 (F-A1-2) · Parallel sign-ins pass the limiter, each spending 19 MiB** · `severity:medium`

- **Severity:** medium: the limiter is weaker than documented (5 per 15 minutes holds only for sequential requests), and memory is spent before sign-in with no cap.
- **Rule broken:** PRD "Nothing is left to a collaborator to bound"; v1 review's sign-in limiter; limits pre-condition (concurrent password checks: none).
- **Steps:** send N wrong passwords at once from one address.
- **Observed:** N × 401, no 429; N × 19 MiB of Argon2id at once. **Expected:** at most 5 verified per window; a cap on concurrent verifications, refused with 429 and `Retry-After`.
- **Impact:** guesses per window equal the attacker's concurrency; 1,000 in flight is about 19 GiB on the Host.
- **Test that would have caught it:** `at most 5 of 20 parallel wrong passwords are verified (the rest get 429)`.

**#82 (F-A1-3) · The sign-in limiter's keys are per address, per IPv6 address, and unbounded** · `severity:low`

- **Severity:** low: hygiene and a documented decision with no recorded end. Moving the limit to a /64 and bounding the map are hardening; the reverse-proxy lockout is accepted in the v1 review with no end date.
- **Rule broken:** PRD "Nothing is left to a collaborator to bound"; limits pre-condition (the sign-in limiter's keys; "the address the limit keys on and `trustProxy` are one decision").
- **Steps:** record failures from distinct IPv6 addresses in one /64, and from 10,500 addresses in one window.
- **Observed:** each address gets 5 tries; every key is held for the window; each failure past 10,000 keys walks the whole map. **Expected:** one key per IPv6 /64; a bound on keys within a window.
- **Impact:** an IPv6 attacker is effectively unlimited; the map grows with the address space; behind a proxy anyone locks the owner out.
- **Test that would have caught it:** `an IPv6 /64 shares one limiter key`; `the limiter holds a bounded number of keys within one window`.

**#83 (F-A1-4) · A logged-out cookie works again after a restart** · `severity:medium`

- **Severity:** medium: the v1 review says restarting signs everyone out; the code says sessions survive a restart, and log out is in memory only.
- **Rule broken:** v1 security review (sessions); FR-29/ADR-0008 log out.
- **Steps:** sign in, log out, restart Lookout (same secret), replay the cookie.
- **Observed:** 200 within the idle period. **Expected:** 401.
- **Impact:** a cookie captured before log out works again after the next update.
- **Test that would have caught it:** `a logged-out cookie stays refused after a restart`.

**#84 (F-A1-5) · A session in use never ends** · `severity:medium`

- **Severity:** medium: no defence in depth; idle expiry is the only bound and every use resets it.
- **Rule broken:** PRD "Nothing is left to a collaborator to bound"; ADR-0008.
- **Steps:** use one session every 6 days for 31 days (idle period 7 days).
- **Observed:** still accepted. **Expected:** an absolute lifetime (figure set in X1b).
- **Impact:** one stolen cookie, kept warm, is access for ever.
- **Test that would have caught it:** `a session in use still ends after 30 days`.

**#85 (F-A1-6) · A weak session secret is accepted at start** · `severity:low`

- **Severity:** low: configuration hygiene; the operator chooses the secret.
- **Rule broken:** PRD "Configuration fails closed" (a short, repeated-character or example secret is refused or warned at start).
- **Steps:** start with `LOOKOUT_SESSION_SECRET=aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa`.
- **Observed:** starts, no warning. **Expected:** refused.
- **Impact:** a guessable secret lets anyone mint sessions (#80 (F-A1-1)).
- **Test that would have caught it:** `a repeated-character 32-byte session secret is refused at start`.

**#86 (F-A1-7) · Behind an HTTPS reverse proxy the cookie is never `Secure`** · `severity:medium`

- **Severity:** medium: the README and the v1 review's accepted risks say the opposite.
- **Rule broken:** v1 review accepted risks; README; FR-29.
- **Steps:** sign in through a TLS-terminating proxy (or with `X-Forwarded-Proto: https`); read `Set-Cookie`.
- **Observed:** no `Secure`. **Expected:** `Secure` behind HTTPS, or the documents corrected.
- **Impact:** the cookie is sent over plain HTTP if the owner ever reaches the same host by `http://`.
- **Test that would have caught it:** `a sign-in forwarded from HTTPS gets a Secure cookie`.

## Load and reach

No request left the pen-test deployment: the deployment probes ran only against `127.0.0.1:7780` or inside its throwaway daemon, and its isolation probe (`e1-isolation.probe.ts`) passed in the same run, in each configuration. The in-process probes opened no socket beyond the app's own. The largest demonstration was 20 parallel sign-ins, from one address inside the deployment; memory for more was worked out by arithmetic only.
