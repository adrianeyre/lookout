# R1: the Host root and Host Metrics — findings

**Scope issue:** #68 · **Date:** 25 November 2026 · **Status:** done; findings fixed and verified 25 November 2026. In-process probes, and deployment probes in both configurations, run before and after the fixes; V2 (#74) checked what a real Host gives.

Hypothesis: [H14](../../product-requirements-document/pen-testing.md#h14-host-root-reads-follow-symlinks--low). Probe tests: [`r1-host-root.test.ts`](../../../apps/server/src/pen-test/probes/r1-host-root.test.ts), [`r1-folders-race.test.ts`](../../../apps/server/src/pen-test/probes/r1-folders-race.test.ts) and [`r1-df.test.ts`](../../../apps/server/src/pen-test/probes/r1-df.test.ts), which run in `pnpm test`, and [`r1-host-root.probe.ts`](../../../apps/server/src/pen-test/probes/r1-host-root.probe.ts) against the deployment (`pnpm pen-test:probe`); each deployment `today_…` probe's `it.fails` partner is the in-process one. Every secret in them is made up.

"In-process" means the real code (the app, `HostRoot`, `DiskReader`, the folder walk) runs against a temporary Host root; anything "outside the Host root" is another temporary directory. These probes don't depend on the configuration: nothing in R1 touches Docker.

The **Largest folders** Widget (FR-14a, merged after the PRD was written) also reads the Host root, so it is in R1's scope.

## Findings to file

### #106 (F-R1-1): Lookout runs as UID 1000, the owner's own account on most Hosts, so it can read their home through `/host`

- **Severity: high.** By the PRD's table, "a compromised Lookout gets more than ADR-0005 and ADR-0011 allow (… a Host file read beyond `statfs`)". With the socket proxy, a compromised Lookout is meant to hold only the allowlist; through `/host` it also holds the owner's SSH keys and registry credentials. In the default configuration it holds Docker anyway, so the increment is the proxy configuration's.
- **Rule broken:** ADR-0003 mounts `/` read-only for Host Metrics. ADR-0011 narrows what a compromised Lookout holds. The v1 review's non-root fix assumes an unprivileged user is less than the owner.
- **Steps:** on a Host whose first user is UID 1000, `docker exec lookout cat /host/home/<user>/.ssh/id_ed25519`.
- **Observed:** readable (by reasoning; the deployment shows the mechanism with a made-up key owned by UID 1000, `0600`). **Expected:** Lookout's UID matches no Host account (for example 65532, or a dedicated UID set in `compose.yaml`), and nothing in `/home` is readable.
- **Test that would have caught it:** `r1-host-root.probe.ts` › `today_ reads a 0600 file the Host's UID 1000 owns…` (turned into "reads no file only a Host user can read"), and V2 on a real VM.

### #107 (F-R1-2): The folder scan lists the Host's directories, beyond `statfs`, against v1 review item 4, with no recorded end

- **Severity: medium.** A control is weaker than its security review says. FR-14a documents the feature, but no ADR accepts it, and v1 review item 4 and the PRD's "Good and to confirm" still say mount points are only `statfs`ed. Folder names under the owner's home (UID 1000, #106 (F-R1-1)) reach every signed-in browser.
- **Expected:** an ADR (or an amendment to ADR-0003) that accepts directory listing and says when that stops being true. The v1 review and the PRD amended. Ideally the scan stays out of `/home` and `/root` unless asked.
- **Test:** `the v1 review's item 4 still describes what Lookout reads under a mount point`.

### #108 (F-R1-3): The Largest folders Widget tells the operator to run Lookout as root

- **Severity: medium.** It undoes the v1 review's non-root fix on the Widget's advice. As root, every Host file (`/etc/shadow` and every key) is readable through `/host`, and a bug in Lookout runs as root.
- **Expected:** no such advice. At most, name the unreadable count.
- **Test:** `never advises running Lookout as root`.

### #109 (F-R1-4): A Container's hard links grow the folder scan's memory without bound, and its folders make the scan endless

- **Severity: medium.** "Nothing is left to a collaborator to bound" and "A Container is an input". The hard-link set holds one key per hard-linked inode a Container makes on the Host's disk.
- **Expected:** a bound on the keys (and on walked entries or time), recorded in the limits table, with the result marked partial past it.
- **Test:** `holds a bounded number of hard-link keys, however many a Container makes`.

### #110 (F-R1-5): The folder walk follows a directory a Container swaps for a link between `lstat` and `opendir`

- **Severity: low.** Only sizes and names that UID 1000 could already list are shown, and only to the signed-in owner. But a Container steers the walk, and the sizes it adds are wrong. A relative link climbs out of `/host` into Lookout's own root. A mount point that is a link is walked at its target.
- **Expected:** open each directory without following links (open the parent and use `O_NOFOLLOW | O_DIRECTORY`; or check after `opendir` that the directory's `st_dev`/`st_ino` match the `lstat`). Skip a mount point that is a link.
- **Test:** `never walks through a directory swapped for a link between lstat and opendir`.

### #111 (F-R1-6): A failed folder scan sends Node's error text, naming the path inside Lookout's Container, to every stream

- **Severity: low.** Disclosure to a signed-in user only. "Every refusal comes from a closed set." Also, one mount point that cannot be `lstat`ed fails the whole scan.
- **Expected:** a fixed text ("The scan could not read a disk") with the detail in the log, and that mount point skipped.
- **Test:** `sends a fixed text, not Node's error with the path under the Host root`.

### #112 (F-R1-7): Folder names, which any Container can write, are shown without `<bdi>`

- **Severity: low.** W1's #89 covers Container text but not the Widget.
- **Test:** `isolates a folder path in <bdi>, like every other piece of Container text (#89)`.

### #113 (F-R1-8): Host-root reads follow links out of the Host root (H14)

- **Severity: low.** On a real Host only the Host's root can make the kernel's mount points or `/etc` links. The effect is wrong data: Lookout's own Image's OS or disk shown as the Host's. In the deployment's fixture root, a link reaches Lookout's own `/etc`.
- **Expected:** a path is resolved and checked against the root before it is read (`realpath` and a prefix check, or skip a mount point or file whose resolved path leaves the root).
- **Tests:** `never reads a Host file through a link that leaves the Host root`; `measures no mount point that is reached through a link out of the Host root`.

### #114 (F-R1-9): `df` is found through `PATH`, not run by an absolute path

- **Severity: low.** Hygiene: the PRD's "Good and to confirm" says it is run by an absolute path. `PATH` is the Image's and the operator's, not an attacker's.
- **Expected:** `execFile('/bin/df', …)` (busybox in the Image), with `--` before the path.
- **Test:** `runs df by an absolute path, not whatever PATH finds first`.

## For V2 (#74), on a disposable Linux VM

Run in the default configuration, as shipped, on a VM with a normal first user (UID 1000):

1. `docker exec lookout id`: the UID and groups, including `DOCKER_GID`.
2. `docker exec lookout cat /host/home/<user>/.ssh/id_*` and `/host/home/<user>/.docker/config.json`, on made-up files the VM's user owns at `0600`. One read, then stop (F-R1-1).
3. `docker exec lookout ls /host/root /host/etc/shadow`: expected refused.
4. `docker exec lookout cat /host/proc/1/mounts`: readable, with resolved mount points, none of them a link (`readlink` each under `/host`). Then `grep -c . /host/proc/1/environ` (expected refused) and `ls /host/proc/1/root` (expected refused).
5. Whether `/host/var/lib/docker`, `…/volumes` and `…/overlay2` can be listed by UID 1000 (Docker makes `/var/lib/docker` `0711 root`: searchable, not listable, so the walk counts it unreadable). Then a Container with a bind mount under the VM user's home (`./data:/data`) writes hard links and a bidi-named folder there, and one Scan now shows whether they are counted and shown. That confirms #109 (F-R1-4), #110 (F-R1-5) and #112 (F-R1-7) on a real Host.
6. With the Widget's advice applied (`user: "0:0"`): the same reads succeed (F-R1-3). Record that, then revert.
7. Destroy the VM.

## Load and reach

No request left the in-process app, and no file outside a temporary directory was read. The deployment probes, once run, read only the deployment's fixture Host root and Lookout's Container inside the throwaway daemon. What they plant is removed in `afterAll`. Nothing ran in parallel; the largest demonstration was 1,524 hard links in a temporary directory.
